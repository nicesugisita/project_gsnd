## 1. 프로젝트 개요

경상남도청의 복지·행정 정보를 AI가 답변해 주는 RAG(Retrieval-Augmented Generation) 챗봇 백엔드입니다.

- 사용자 질문 → 문서 검색 → LLM 응답 생성의 3단계 흐름
- 스트리밍(`SSE`) / 비스트리밍 모드 모두 지원
- 경상남도 내 시·군 특화 필터링, 생애주기 기반 복지 추천 기능 내장

---

## 2. 기술 스택

| 영역 | 기술 |
|---|---|
| 웹 프레임워크 | FastAPI (Python 3.12) |
| 설정 관리 | pydantic-settings (.env 기반) |
| LLM 연동 | httpx AsyncClient (내부 OpenAI 호환 API) |
| 벡터 검색 엔진 | Mariner (Java 기반, JPype로 Python에서 JVM 직접 호출) |
| DB | MySQL (mysql-connector-python, 커넥션 풀) |
| 비동기 HTTP | httpx (LLM, DeepServer, TTS 클라이언트 공유 풀) |
| STT | WebSocket 기반 외부 서버 |
| TTS | HTTP 기반 외부 서버 |
| 형태소 분석 | kiwi (키워드 추출용) |

## 4. 앱 기동 순서 (Entry Point)

**설명 시작점**: `src/app/main.py` → `src/app/application.py`

```
uvicorn app.main:app
    └─ create_app()                          # application.py
        ├─ _setup_logging()                  # 로그 파일·포맷 초기화
        ├─ FastAPI 앱 생성 + CORS 미들웨어
        ├─ 도메인 라우터 7개 등록
        └─ lifespan 연결                     # core/lifespan.py
```

**lifespan (startup)** — `src/app/core/lifespan.py`

앱이 첫 요청을 받기 전 아래 순서로 자원을 초기화합니다:

1. `_init_jvm()` — Mariner 검색을 위한 JVM 기동 (JPype, JAR 로드)
2. `_init_llm_client()` — LLM용 httpx AsyncClient 생성 (커넥션 풀)
3. `_init_ds_client()` — DeepServer용 httpx AsyncClient 생성
4. `_init_db_pool()` — MySQL 커넥션 풀 초기화
5. `_init_retriever()` — MarinerRetriever 인스턴스 생성
6. `_preload_prompts()` — 디스크의 프롬프트 파일을 lru_cache에 워밍업

모든 자원은 `app.state.*`에 저장되어 요청 핸들러에서 `request.app.state.llm_client`로 접근합니다.

## 5. 설정 관리

**파일**: `src/app/core/config.py`

- `pydantic-settings`의 `BaseSettings`를 상속한 `Settings` 클래스 하나가 Single Source of Truth
- 우선순위: **환경변수 > .env 파일 > 필드 기본값**
- `.env` 위치: 프로젝트 루트
- `@lru_cache`로 싱글톤 보장: `get_settings()` / `Config` (alias)

주요 설정 그룹:

| 그룹 | 키 예시 |
|---|---|
| LLM | `LLM_API_URL`, `LLM_ENABLED`, `LLM_API_TIMEOUT` |
| RAG | `RAG_COLLECTION`, `RAG_OKMS_COLLECTION`, `RAG_THRESHOLD` |
| Mariner | `MARINER_IP`, `MARINER_PORT`, `JAR_LIB_PATH` |
| DB | `DB_HOST`, `DB_USER`, `DB_POOL_SIZE` |
| STT/TTS | `STT_WEBSOCKET_URL`, `TTS_SERVER_URL` |
| 세션 | `SESSION_TIMEOUT_MINUTES`, `MAX_CONCURRENT_USERS` |

## 6. 도메인별 구조

각 도메인은 `router.py`(엔드포인트) → `service.py`(비즈니스 로직) → `infra/`(외부 연동) 계층으로 구성됩니다.

### 6-1. `chat` — 핵심 도메인

채팅 응답 생성 전체를 담당합니다. 아래 7장에서 상세 설명합니다.

**주요 엔드포인트** (`router.py`):

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/v1/chat/completions` | 메인 채팅 응답 (스트리밍/비스트리밍) |
| POST | `/v1/chat/recommend/collect` | 복지 추천 시작 (지역·출생연도 수집) |
| POST | `/v1/chat/suggest-questions` | 후속 질문 추천 생성 |

### 6-2. `conversation` — 대화 이력

**주요 엔드포인트**:

| 메서드 | 경로 | 설명 |
|---|---|---|
| GET | `/v1/chat/conversations` | 사용자의 대화 목록 조회 |

| DELETE | `/v1/chat/conversations/{conv_id}` | 대화 삭제 |
| POST | `/v1/chat/messages/feedback` | like/dislike/copy 피드백 저장 |

### 6-3. `document` — 문서 관리

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/v1/files/upload` | 파일 업로드 |

## 7. 핵심: 채팅 파이프라인 흐름

`POST /v1/chat/completions` 요청이 들어오면 아래 순서로 처리됩니다.

### 7-1. 진입 및 기본 검증 (`router.py`)

```
요청 수신
 ├─ JSON 파싱 + ChatRequest 생성
 ├─ _ensure_runtime_user_id()      # 비로그인 사용자에 임시 ID 부여 (nologin+conv_id)
 ├─ 로그 컨텍스트 설정 (conv_id, user_id)
 ├─ _merge_and_init_conversation()  # 대화 세션 초기화·병합
 ├─ 메시지 검증
 └─ guide_recommend 모드면 → 바로 RAG 처리로 분기
```

### 7-2. 스트리밍 vs 비스트리밍 분기

- **스트리밍** (`stream=True`): `_streaming_chat_flow()` 비동기 제너레이터 → SSE(`text/event-stream`)
- **비스트리밍**: `router.py` 내에서 동일 단계를 순차 실행 → JSON 응답

이하 단계는 두 경로 모두 동일하게 적용됩니다.

### 7-3. 파이프라인 단계 (`_pipeline_steps.py`)

| 단계 | 함수 | 설명 |
|---|---|---|
| **[1] Pre-Check** | `run_pre_check()` | LLM이 RAG 필요 여부 판단 + 되묻기(clarification) 감지 |
| **[2] 조기 시군 확인** | `run_early_sigun_check()` | 되묻기 답변 직후 시·군 조기 확정 |
| **[3] 쿼리 재구성** | `_run_query_recreation()` | 멀티턴 대화에서 완전한 검색 쿼리 재생성 (LLM) |
| **[4] 범위 체크** | `run_out_of_scope_check()` | 경상남도 외 지역 감지 → 안내 메시지 반환 |
| **[5] 시군 체크** | `run_sigun_check()` | 시·군 확정 또는 되묻기 (최대 3회 후 포기) |
| **[6] 통합 전처리** | `run_unified_preprocess()` | 단일 LLM 호출로 4가지 동시 처리 (↓ 상세) |
| **[7] 생애주기 체크** | `run_lifecycle_check()` | guide_recommend 모드 전용 로그 |
| **[8] RAG 실행** | `_get_rag_processor(intent)` | 의도별 RAG 함수 선택 후 실행 |

### 7-4. 통합 전처리 (`preprocessing.py`)

**단일 LLM 호출로 4가지 작업을 동시에 처리**하는 최적화 핵심 포인트입니다.

```
입력: user_query + 최근 3턴 대화 이력
      ↓ (LLM 1회 호출, temperature=0, JSON 응답)
출력:
  ├─ query          : 맞춤법·표준어 정제된 질문
  ├─ intent         : general | comparison | guide_recommend | search
  ├─ intent_reason  : 의도 판단 근거
  ├─ reformed_query : 검색 최적화된 질의
  └─ expanded_queries : 다각도 확장 질의 목록
```

### 7-5. "더 알려줘" 처리 (`_streaming.py`)

스트리밍 경로에서는 전처리 전에 `_resolve_more_results_context()`가 실행됩니다.  
`MORE_INFO` 의도가 감지되면 이전 검색 결과(reformed_query)를 재사용하고,  
기존에 노출된 문서(chunk_id, 서비스명)를 제외 목록에 추가하여 새 문서를 탐색합니다.

## 8. RAG 파이프라인 상세

의도별로 별도 파이프라인 파일을 사용합니다.

| 의도 | 파일 | 설명 |
|---|---|---|
| `general` | `pipeline_general.py` | 일반 복지·행정 질문 |
| `comparison` | `pipeline_comparison.py` | 두 서비스 비교 질문 |
| `guide_recommend` | `pipeline_guide_recommend.py` | 맞춤형 복지 서비스 추천 |
| `search` | `pipeline_search.py` | 키워드 단순 검색 |

### 쿼리 확장의 출처

`expanded_queries`는 **통합 전처리 LLM 1회 호출** (`unified_preprocessing_prompt.txt`) 결과물입니다.
DeepServer `expand_query()`는 precomputed 값이 없을 때만 작동하는 폴백 경로입니다.

| 경로 | 쿼리 확장 출처 | 조건 |
|---|---|---|
| 일반 흐름 (general/comparison/search) | 통합 전처리 LLM (`unified_preprocessing_prompt.txt`) | 항상 |
| guide_recommend 단축 경로 | DeepServer `expand_query()` (PROMPT_ID=2) | precomputed 없을 때 |

RAG 파이프라인은 `precomputed_expanded_queries`가 전달되면 DeepServer 호출을 생략하고,
키워드도 마찬가지로 `precomputed_keywords`가 있으면 `/rag/extract-keyword` 호출을 건너뜁니다.

### general 파이프라인 흐름 (가장 복잡, 기준 설명)

```
[Step 1] 쿼리 확장
         ├─ precomputed_expanded_queries 있으면 → 통합 전처리(unified_preprocessing_prompt.txt) 결과 사용
         └─ 없으면 → expand_query() → DeepServer 폴백

[Step 2] 키워드 추출
         ├─ precomputed_keywords 있으면 → filter_okms_keywords() 적용
         │   (첫 번째 확장쿼리에만 매핑, 나머지 빈 리스트)
         │   (출처: 통합 전처리 내 kiwi가 reformed_query에서 명사 추출)
         └─ 없으면 → extract_triples() → DeepServer /rag/extract-keyword (확장쿼리별 병렬)
                      → 각 결과에 filter_okms_keywords() 적용
         공통: _build_search_queries() → 키워드 검색 문자열 구성

[Step 3] 필터 추출
         ├─ SIGUN  : 파이프라인 인자로 사전 확정됐으면 그대로 사용
         │           없으면 메시지에서 추출 → normalize_sigun()
         ├─ LIFECYCLE : 출생연도 → 생애주기 변환 (없으면 대화 히스토리에서 추출)
         └─ YEAR   : extract_year_filters() → 연도 언급 감지

[Step 4] OKMS Group A + GOV_OKMS 병렬 검색
         └─ asyncio.gather() + run_in_executor()  ← 동기 Mariner 호출을 스레드 풀로 격리
         ├─ GroupA 벡터 검색  : 확장쿼리별 vector_docs (SIGUN·YEAR·LIFECYCLE 필터 적용)
         ├─ GroupA 키워드 검색 : 키워드쿼리별 keyword_docs
         └─ GOV_OKMS 검색     : 확장쿼리 + 키워드쿼리 (LIFECYCLE·SIGUN 필터만 적용)

[Step 5] 상위 문서 선택
         └─ GroupA + GOV_OKMS 결과 중복 제거 후 가중치 내림차순 상위 8건 선택

[Step 5-F] OKMS Fallback (결과 1건 미만일 때)
           └─ 연도·생애주기 필터 제거, 시군 필터만 유지하여 재검색 후 기존 결과와 합산

[Step 5-S] OKMS 적합성 판단 (LLM — 8b/sllm)
           └─ retrieval_sufficiency_judgment() → sufficient: bool
           ├─ sufficient=True  → OUR_REGION_TEL / GSND 검색 생략
           └─ sufficient=False → Step 6으로 진행

[Step 6] OUR_REGION_TEL 검색 (OKMS 부족 시)
         └─ 읍·면·동 기반 복지 연락처 컬렉션 검색

[Step 6-S] OKMS + OUR_REGION_TEL 통합 적합성 판단 (LLM — 8b/sllm)
           ├─ sufficient=True  → GSND 검색 생략
           └─ sufficient=False → Step 6-B로 진행

[Step 6-B] GSND 보강 검색 (OKMS + OUR_REGION_TEL 모두 부족 시)
           └─ (fallback 확장쿼리 or 확장쿼리) + 키워드쿼리 병렬 검색 후 상위 2건만 보강

[Step 6 합산] OKMS + OUR_REGION_TEL + GSND 중복 제거 후 가중치 내림차순 정렬

[Step 7] 관련성 필터 (LLM — 8b/sllm)
         └─ filter_irrelevant_docs() → 무관 문서 제거

[Step 7-1] 관련성 필터 결과 0건이면 → GroupA 하위 문서로 재시도

[Step 7-2] 0건이거나 제외 문서(excluded) 있으면 → OKMS Fallback 재검색 후 관련성 필터 재적용
           └─ excluded 문서 제거 후 관련성 필터

[Step 7-3] 최종 0건 → "답변을 찾을 수 없습니다" 반환

[Step 8] 정렬
         └─ 상위 30% → 최신순(YEAR) / 나머지 → 가중치(WEIGHT) 내림차순

[Step 9] 참고 문서 구성
         └─ build_referenced_documents() → UI 표시용 메타데이터 (id, chunk_id, name, snippet)

[Step 10] 최종 응답 생성 (LLM — 32b/luxia)
          └─ generate_final_response_v2()
             ├─ 의도별 프롬프트 선택 (general / comparison / guide_recommend / search)
             ├─ 재구성된 사용자 질의 + 검색 문서를 단일 user 메시지로 LLM 호출
             └─ stream=True면 스트리밍 제너레이터 반환
```

### Mariner 검색 엔진 (`mariner/`)

- **Java 기반 벡터 검색 엔진**으로, `jvm_manager.py`가 서버 기동 시 JVM을 1회 초기화합니다 (싱글톤, JPype).
- 각 `queryset_*.py` 파일이 JPype를 통해 Java 클래스를 직접 호출합니다.
- Mariner 호출은 **동기(blocking)** 이므로 비동기 파이프라인에서 반드시 `run_in_executor()`로 스레드 풀에서 실행합니다.
- **Fallback 전략**: 연도·생애주기 필터 적용 검색 → 결과 부족 시 해당 필터만 제거하고 재검색 (시군 필터는 유지)

| 파일 | 대상 컬렉션 | 설명 |
|---|---|---|
| `queryset_okms.py` | OKMS | 사업 복지 카드 문서 (벡터+키워드 듀얼 검색) |
| `queryset_okms_fallback.py` | OKMS | Fallback 전용 (연도·생애주기 필터 제거) |
| `queryset_gov_okms.py` | GOV_OKMS | 정부 기관 사업 복지 카드 문서 |
| `queryset_welfare_tel.py` | WELFARE_TEL | 복지 연락처 (OUR_REGION_TEL) |
| `queryset_gsnd.py` | GSND | 경남도청 일반 행정 문서 (보강용) |
| `queryset_gsnd_fallback.py` | GSND | GSND Fallback 전용 |
| `queryset_welfare.py` | WELFARE | 복지시설 정보 |
| `queryset_upload.py` | UPLOAD | 사용자 업로드 문서 |

## 9. 외부 서비스 연동

### LLM API (`infra/llm/`)

- `client.py`: `call_llm_api()` — OpenAI 호환 API를 httpx로 비동기 호출
- `judgment.py`: `pre_check()` — RAG 사용 여부 + 되묻기 판단
- `preprocessing.py`: 텍스트 정제, 표준어 변환, 음성 출력 최적화

### DeepServer (`infra/deepserver/`)

- 쿼리 재구성 (`deepserver_reform_query`)
- 쿼리 확장 (`deepserver_expand_query`)
- 비교 속성/트리플 추출 (`deepserver_extract_comparison_*`)

### STT (`infra/stt/`)

WebSocket 기반 음성 인식 서버와 연동합니다.

### TTS (`tts/`)

HTTP POST로 텍스트 전송 → WAV 오디오 반환.  
`infra/` 하위에 한국어 TTS 전처리 파이프라인이 있습니다:

```
원문 텍스트
  → normalizer (숫자, 날짜, 전화번호, 주소, 영문 등 한글 변환)
  → segmenter (문장 분절: classifier → splitter → merger)
  → parser (최종 발음 표기 생성)
  → TTS 서버 전송
```

## 10. 부가 기능

### 시·군 되묻기 (`chat/sigun.py`)

- `location_dict.json`으로 읍·면·동 → 시·군 매핑
- 질문에서 경상남도 시·군 추출 실패 시 → 되묻기 메시지 반환
- 최대 3회 시도 후 포기 메시지 반환

### 로그 컨텍스트 (`core/logging_context.py`)

- `set_log_context(conv_id, user_id)`로 요청별 컨텍스트를 스레드 로컬에 저장
- 모든 로그에 `conv_id`/`user_id`가 자동 포함되어 요청 추적이 용이

### 타이밍 CSV 기록 (`_streaming.py`)

스트리밍 응답 완료 후 구간별 소요시간을 `tests/log_YYYYMMDD.csv`에 기록합니다.  
성능 분석·병목 파악에 사용됩니다.

### 프롬프트 관리 (`shared/utils/prompt_loader.py`)

- 모든 프롬프트는 `prompts/` 디렉토리의 텍스트 파일로 관리
- `lru_cache`로 캐싱 → 서버 기동 시 `_preload_prompts()`로 워밍업
